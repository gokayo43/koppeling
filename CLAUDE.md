## Canon

The house rules live outside this repo and win over anything here:
`~/claude-shared/STACK.md` (one pick per slot), `architecture.md` (module
vocabulary, depth, the docs spine), `testing.md` (oracles, the rewrite test),
`principles.md` (day-0 native, supersede-don't-accrete, the issue queue).

Inside the repo: `CONTEXT.md` is the domain glossary and this file is
everything else, both updated by the change that makes them true. A why lives
at its tightest anchor — a comment at the code it governs, or "Gotchas" below
when it belongs to the whole repo — and a decision that is not yet due is a
trigger-bearing issue rather than a document.

## Layout

<!-- scaffold:single -->

One package. The browser app is `src/routes/` + `src/components/`, server code is
`src/server/` (schema, database, auth, the Effect runtime), and `src/domain/` is
the pure core. Server logic lives in Start server routes and server functions;
there is no separate API program.

`src/server.ts` replaces the Start plugin's default server entry — the plugin
resolves `src/{client,server,start,router}` and falls back to its own. It exists
for one line: under `ROUTE_LOG` it wraps the request handler in
`src/server/route-log.ts`, which counts what each route takes and serves the
tally on `/__route-log` for CI's route-coverage floor. Unset, the wrapper hands
the handler straight back, so a deployment carries no instrument and no
endpoint.

<!-- scaffold:monorepo -->

Bun workspaces. `apps/web` is the browser app and nothing else — it reaches the
server over the Eden treaty client in `apps/web/src/lib/api-client.ts`, typed
against the API program's own `App` type. `apps/api` owns the database, the
schema, auth and the Effect runtime, and exports its routes to no one but Eden.
`apps/web/src/domain/` is the pure core.

## Commands

```sh
bun run dev          # dev server(s)
bun run check        # format:check + lint + typecheck + knip — the static CI gate
bun test             # unit + property + PGlite schema tests, coverage-floored
bun run db:generate  # drizzle-kit: emit a migration from the schema
bun run db:migrate   # apply pending migrations (also the compose migrate service)
```

`bun run build` has to run before `typecheck` or `lint` on a clean checkout:
`routeTree.gen.ts` is generated by the Start plugin and is not committed, so
`tsc` and the type-aware lint rules would report its symbols as missing. CI does
this in the same order.

<!-- scaffold:monorepo -->

`dev`, `build` and `typecheck` are `turbo run` over the workspaces: each app owns
its own script and the root only delegates, so a lane whose inputs have not moved
replays from the local cache instead of running again. `test` deliberately does
not — `bun test` walks the whole tree in one process and CI reads a single junit
report out of it. That holds only while every app's tests CAN share one process:
a repo whose apps need different runners, different environments or different
lanes routes `test` through turbo too and gives each app its own script
(fastlol is that repo). `lint`, `format` and `knip` stay single root passes for
a reason that does not expire: one invocation already sees everything. The
root's own files (`knip.ts`, `scripts/`) belong to no workspace, so they have
`typecheck:root`, a turbo root task that `bun run typecheck` names alongside the
fan-out. Remote caching is off until CI time is a measured problem.

`setup/ci.<shape>.yml` is the scaffolded repo's CI: it sits outside
`.github/workflows` so GitHub does not run it against a template that has no
dependencies yet, and `bun run setup` moves whatever it finds under `setup/*.yml`
into place — a file named for a shape installs as `ci.yml` for that shape only.
That directory is the list: the scaffolder globs it, and this repo's own gate
lints every file in it as a workflow. One per shape rather than one carrying a
region per differing line, because a key two shapes need different values for
cannot be written twice in one `with:` — the price is a few duplicated lines of
preamble, which is the cheap side of that trade.
`.github/workflows/template.yml` is the only workflow that stays here, and it
is this repo's own gate: it scaffolds both shapes into a copy, runs the whole
scaffolded gate against each, and then typechecks, lints and format-checks
`setup.ts` — the one file no scaffolded repo can gate, because the scaffolder
deletes itself. None of it survives into the repo it produces.

What follows describes the workflow the scaffolded repo keeps.
<!-- scaffold:template -->

`.github/workflows/ci.yml` is a call into `dev-config`'s `check.yml`, pinned to
a commit SHA — the gate itself is shared, and this repo passes only what is its
own.

Before the install it runs the declarative gates: the repo contract (the strings
every other gate rests on — `packageManager`, the config lineage, `bunfig.toml`,
the hooks, the shape of the secrets, the docs spine, the pinned CI call), the
stack denylist, suppression hygiene, and the compose lint. They read the tree as
committed, so drift is a red build in seconds rather than after a full
dependency resolution.

What it adds on top of the commands above is a database no local run has: an
empty Postgres, every migration replayed onto it twice with `pg_dump` proving the
second pass changed nothing, an assertion that no column is `timestamp without
time zone`, and then a boot against the result.

The boot ends in a k6 ramp, with no knob to forget: an app the database job can
start is an app that serves something, and a route nothing has ever put under
load is what the floor beside it refuses. What the workflow chooses is where the
load goes — `capacity-path`, and `route-allowlist` for a route the ramp cannot
reach, each entry carrying its own `-- why`. That number is a trend line against
the last run and never a capacity claim; the claim comes from
`scripts/preview-capacity.sh` below.

That 200 is worth more than a socket: the health route's probe reads a migrated
table's own columns, so it answers only once the migrations have produced the
schema the code queries. An app pointed at an empty database reports degraded,
which is what an orchestrator should be told about an instance that cannot serve.

A migration that only applies to an already-migrated database fails there rather
than on a deploy or a restore drill.

The day this database is deployed somewhere, add `upgrade-gate: true` beside
`database: true` in that workflow. It proves the other half: a database built
from the base ref's migrations and upgraded by this branch's reaches the schema
a rebuild does. From the first deploy the lineage is a one-way record — editing
a migration that has already run is a silent no-op on every database that has
seen it — and until then, rewriting it is free.

CI also asserts the suite reported no skipped and no assertion-free tests, so a
suite that quietly stopped running cannot pass for a green one. **Assert with
`expect`, properties included** — a fast-check predicate that returns a boolean
records no assertion, and a property that never ran looks exactly like one that
passed.

<!-- scaffold:single -->
After the suite comes the mutation lane, which asks what coverage cannot: change
the code, and see whether anything fails. It mutates the files a branch changed
under `src/domain/` — read from the `domain` boundaries element in
`.oxlintrc.json`, the same declaration the layer rule uses — and fails on a
mutant sitting on a line that branch wrote. A branch that changed nothing there
is a pass that says so.

The score goes to the run summary either way, and no `mutation-floor` sits
beside it: what the lane catches is domain code that arrived without the test
that pins it, which is a statement about the branch rather than a number to hold
the repo to. Add a floor once the domain's own score comfortably clears one.

It is a CI gate and only a CI gate — there is no local equivalent to run. The
step writes Stryker's config itself, including the empty `tsconfigFile` that
keeps Stryker's tsconfig rewrite away from a TypeScript API this stack's
compiler does not export; a bare `bunx stryker run` in this repo dies on that
call before it tests a mutant. `docs/gates/mutation-lane.md` in dev-config is
where all of it is argued.

## Worktrees

`bun run dev` and `db:migrate` derive an isolated world when they run inside a
**linked git worktree** — a database `<app>_wt_<branch>` on the dev compose
Postgres, and dev ports out of a block this branch's name picks — and print what
they derived — a worktree's `SITE_URL` among them, because a browser reaching
the port it was given has to find an app that answers at it. Nothing to remember
beyond `bun install`.

The primary checkout keeps its own database and its own ports, and the wrapper
holds it to two things. Its env files may name nowhere but this machine, over
plain http ("Deploy" below) — all of them, since bun and vite each load several
and disagree about which wins. And the port `bun run dev` binds is the one its
`SITE_URL` names: pass `DEV_PORT` to move both at once, because vite refuses a
taken port rather than sliding onto one the app never tells the browser about.

Only those two: the suite runs on an in-process PGlite and `db:generate` never
connects, so neither reads anything derived and neither goes through the
wrapper. A test that needed the dev database would be the wrong test — that is
what makes this safe to leave unwrapped. Of the two, only `dev` claims ports:
it is the one that binds them.

The primary checkout's `.env` is the shared configuration: a worktree never has
one of its own, and the wrapper reads it and layers over it rather than writing
to it. The worktree's gitignored `.env.worktree` records one thing, the ports it
claimed — probed once inside the block, then kept, so a second command cannot
step onto a different port while the first is still serving. Delete it to be
given new ones.

A claim is only good for the block the branch's name picks now: switch branches
inside a worktree and the old ports are discarded rather than carried over,
because carrying them over is how two worktrees end up on one port, each serving
the other's database. And a claimed port that something else is already holding
is refused by name — never quietly moved, because that port has been reported,
written down and, in the monorepo, baked into the web app's API URL. Two first
commands started at once can still both probe before either writes; the second
is stopped at that refusal rather than half-starting.

- **Worktree worlds are disposable.** The primary checkout's dev database is the
  stable one. Experimental or WIP code points at its own derived world and
  nothing else, ever.
- **A worktree needs a branch.** A detached HEAD is refused rather than derived
  from: every detached worktree would answer `HEAD` and share one database.
- **Redis is not isolated**, where a shape has one: nothing in the template keys
  off a prefix, so a worktree shares the dev instance. A queue or cache is what
  makes per-worktree keyspace worth deriving.
- `bun run worktree:clean` drops the databases whose branch is gone, and says
  what it dropped and what it kept. Only the `<app>_wt_` names this tooling
  creates are ever candidates. It is never automatic — a database outlives
  `git worktree remove`, and dropping one does not come back.
- **Known seam:** two worktrees generating migrations will collide in drizzle's
  journal when they rebase. Regenerate after rebasing. Git surfaces the conflict
  and nothing here hides it.

## Preview

```sh
scripts/preview.sh                          # real images, own database, own ports
scripts/preview.sh --restore --key <file>   # ...from the latest backup, which is a restore drill
scripts/preview-capacity.sh                 # ramp what is running, write the number to capacity/
scripts/preview-down.sh                     # gone, volumes included
```

`preview-capacity.sh` is the capacity measurement testing.md asks for before
real users arrive and again after a change to a hot path: the same ramp, the
same reader and the same failure bound CI uses — all of them dev-config's, out
of `node_modules` — against the images that would ship, on the box that would
run them. It reaches the preview project's own ports and refuses outright when
that project is not up, because a load generator that found the deployed stack
instead is a load test against production. `--dry-run` prints what it would ramp
and stops.

Its own compose project (`-p <app>-preview`), so it cannot reach the running
stack on this box. Once a repo has real users this is the pre-deploy smoke path:
the images are the ones that would ship, and `--restore` is the only way to find
out a backup is unreadable before the night it is needed — it hands the archive
to `scripts/restore-drill.sh`, so the rehearsal is the drill. Its key is the
private age identity, which `BACKUP_AGE_KEY` in `.env` names — README,
"Backups". `preview.sh` passes `--project`: a stack the caller already has up,
which the drill fills and neither starts nor stops — that is why the preview's
own Postgres goes up first. The timer passes `--scratch-project`. What the two
flags mean, and why neither may name the deployed project, is in the drill's own
header, which is the single home for it. Migrations run either way, and
after the restore: a backup is older than the code being previewed, which is the
deploy being rehearsed.

## Deploy

nginx serves the hostname from `infra/nginx/`, proxying to the compose stack on
127.0.0.1.

<!-- scaffold:monorepo -->
Two hostnames out of that one file: the web app on the site's, the API on
`api.<site>`. Why a name of its own rather than a path under the web app's —
the two browser clients do not treat a prefixed origin alike, and the one that
refuses cannot be talked round — is written at the block that serves it, which
is where it stays. So a deploy points both names at this box and the origin
certificate carries both.

<!-- scaffold:monorepo -->
Where a deployment answers is `deploy.env`, and nowhere else: compose hands that
file to the containers, `env_file`, while a checkout's `.env` answers the same
question about this machine. Nothing ever moves one into the other — this box is
a deploy target as well as a checkout, so a single file for both is a dev server
serving the deployed origins or a deployment serving loopback. `bun run dev`
refuses a `.env` whose origins are not this machine over plain http, and
`scripts/env-wiring.test.ts` holds `deploy.env` to the hostnames `infra/nginx/`
actually serves. `scripts/preview.sh` writes a file of the same shape and points
compose at it with `ORIGINS_ENV`, which is why the name is a variable.

<!-- scaffold:monorepo -->
The web image's build reads that file too: compose cannot hand a build the
`env_file` its services read, so it passes the name and `Dockerfile.web` takes
the API origin out of it — vite inlines `import.meta.env` at build time, so the
browser bundle carries the origin rather than reading one.

<!-- scaffold:monorepo -->
```sh
sudo docker compose build && sudo docker compose up -d
```

**The app builds INSIDE the image.** `up -d` on its own restarts containers from
the image that is already there and deploys nothing — editing source and running
`up -d` is the single most common way to convince yourself a fix shipped when it
did not.

Migrations are a one-shot `migrate` service the app waits on with
`service_completed_successfully`, so a failed migration leaves the previous
containers running instead of starting new ones against a schema they do not
match.

CI holds `docker-compose.yml` to that shape: every port on `127.0.0.1`, a
`mem_limit` on every service, a healthcheck on every service or an
`x-no-healthcheck: "<test path> -- <why>"` naming the committed test that asserts
it can never answer one, and every service built from this repo waiting on
`migrate`.

## Going live

`package.json` carries one field, and nothing infers it:

```json
{ "lifecycle": "dev" }
```

A repo with a hostname, a compose file and a backup script looks exactly like
one three days from its first deploy, and the difference is the whole
difference. So the repo says which it is, a scaffold says `"dev"`, and moving it
to `"live"` is the owner's own commit — made when this starts serving real
people, not before.

It only moves up. The contract reads the field at the base ref as well, so
writing `"dev"` back over `"live"` — or deleting the line — is refused rather
than merged as tidying. A repo genuinely being wound down says so by naming
`lifecycle-retire` in `contract-exemptions`, which is a decision someone reviews
rather than a diff nobody notices.

That one word is the only thing to remember. The repo contract derives the rest
from it and names by hand whatever is not yet true — crash reporting, and, for a
repo that owns migrations, the backups, the rehearsed restore and the upgrade
gate. `docs/gates/repo-contract.md` in dev-config is the list, and it is the list
because that is where the code enforcing it lives; a copy here would be a second
one to keep true.

Take the capacity number before you flip it — `scripts/preview.sh`, then
`scripts/preview-capacity.sh` — since after real users arrive it is a
measurement of production.

## Work queue

GitHub Issues, and they are this project's memory across sessions rather than
something a human reads. An open issue with no label is new; GitHub's close
reasons say how a closed one ended. Three labels carry what nothing else does:
`roadmap` (agreed direction, no date), `commitment` (the body states a
**Trigger:**) and `parked` (the owner has seen it and not decided). Approval
happens in conversation. Nothing in CI touches any of this; the rules are in
`~/claude-shared/queue.md`.

## Conventions

- **An agent that boots the app reports the URL in its final message.** Always,
  and the one it actually got — a derived worktree port is not the default, and
  a URL nobody printed is a server nobody looked at.
- **Temporal, not `Date`, on the server.** Store UTC. Client code uses
  `date-fns-tz` until Safari ships Temporal.
- Server dialect is Effect: `runtime.ts` is the composition root, and
  `runtime.runPromise` at the edge is the only place an Effect leaves the Effect
  world. Plain TypeScript is allowed for a pure CRUD membrane over the database,
  and only when the change that introduces it adds a Gotchas bullet naming the
  modules it covers and the boundary past which Effect resumes.
- Validation at trust boundaries only — `env.ts` parses the process environment
  once and every other module reads the parsed value.
- The `domain` layer is pure: the linter denies imports from it into server or
  route code, and that is what keeps it testable without a database.
- Secrets: `.env` is gitignored, `.env.example` is its shape, and `.env.enc` is
  the committed age-encrypted copy. Nothing else holds credentials. A
  `<environment>.env` — `deploy.env`, and the `preview.env` a preview writes —
  is the other kind of file: public origins, handed to containers, loaded by no
  checkout and by no vite mode.

## Gotchas

Whys that belong to the repo rather than to one line of it. Anything narrower
is a comment at the code it governs, pointed at from here rather than repeated.

- **Nothing binds every interface unless a container asks.** The Nitro output
  takes its bind address from `HOST` and binds everything without one, and
  nothing outside a container sets it — so the `start` script defaults it to
  loopback. That default lives in a `package.json` string with nowhere to carry
  a comment, which is why its reason is here. Every image that EXPOSEs a port
  carries `HOST=0.0.0.0` — set in its own stage or inherited from the one it was
  built from, since either reaches the container: a container has to be
  reachable from the compose network, and compose still publishes the port on
  127.0.0.1 alone. Started by hand on a dev box — a worktree's server on a
  derived port — a wide bind is a real database behind a port anything that can
  route to this machine can open. `scripts/bind.test.ts` starts what a test can
  start and reads back what the kernel says it bound; it reads the images and
  the dev server's config instead.
<!-- scaffold:monorepo -->
- The API states that same rule in code: `HOST` in `apps/api/src/env.ts`.
- One key says where the API is, and both ends read it: `PUBLIC_API_URL`. The
  web image bakes it into the browser bundle — `apiUrl` in
  `apps/web/src/lib/api-origin.ts`, whose docstring says why it is never spelled
  `VITE_` anything — and the API takes it as the origin Better Auth issues from.
- **The session cookie is widened to the site's hostname**, because the browser
  signs in against `api.<site>` and reads the session on `<site>`. Which domain,
  and when there is none to widen to, is `apps/api/src/cookie-domain.ts`: a dev
  or preview pair on one loopback host gets nothing, and a pair that could never
  share a cookie — a site behind `www.` in front of the same `api.` — stops the
  program at boot rather than serving sign-ins the browser forgets.
- **An Elysia hook covers the routes registered after it, and no others.**
  Request logging, metrics, tracing, auth telemetry — anything that needs the
  matched route or the response — is `.use()`d as a plugin at the head of
  `apps/api/src/app.ts`. Added to the composed app in `main.ts`, where the
  finished instance is in hand, it typechecks, runs, and observes zero requests,
  `{ as: "global" }` included; the first sign is a dashboard that stays empty.
  That is why no Elysia instance leaves `app.ts` — the docstring above the
  composition there carries the measurement.

## Framework current state

Verified on 2026-08-03 against `@tanstack/react-start` 1.168.32,
`@tanstack/react-router` 1.170.x, `vite` 8.1.5, `nitro` 3.0.260610-beta,
`@vitejs/plugin-react` 6.0.4, `drizzle-orm` 0.45.2, `bun` 1.3.11. Re-check
before trusting any of it against a newer set.

- **Start's server routes are file-based.** A file in `routes/` exporting
  `createFileRoute("/api/health")({ server: { handlers: { GET } } })` is the
  whole registration. The `nitro({ handlers: [...] })` list older repos here use
  is no longer needed.
- **The dev server has to run under Bun, and the `dev` script says so.** `vite`
  ships a `#!/usr/bin/env node` shebang, so a plain `vite dev` serves under Node,
  where Drizzle's `bun-sql` driver cannot resolve its `bun` import: every route
  that touches the database answers 500 while the build stays green. `bunx --bun`
  is what makes the dev server Bun.
- **`PORT` belongs to the API, so the web's dev script drops it.** The Start
  plugin's dev server takes `PORT` over anything `vite.config.ts` sets, which in
  the monorepo would put the web app on the API's port; `env -u PORT` in front of
  `vite dev` is what keeps `DEV_PORT` authoritative.
- **A dev server is a task that never exits, and turbo has to be told.** The
  monorepo's `dev` task is `persistent: true` in `turbo.json`; without it turbo
  treats each dev server as a step its dependents wait on, and the web app waits
  forever on an API that is running fine. `cache: false` beside it is the other
  half — there is no output to replay.
- **Nitro's output is `node-server`, not a Bun target.** It boots under Node and
  serves pages. What forces Bun in production is our own driver: Drizzle's
  `bun-sql` adapter imports `bun`, so under Node the server starts and then
  answers 500 with `ERR_MODULE_NOT_FOUND: 'bun'` on the first route that touches
  the database.
- **`bun` has to be declared external.** It is a runtime builtin with no package
  behind it, so without `build.rolldownOptions.external: ["bun"]` the Start SSR
  build fails outright: _Rolldown failed to resolve import "bun"_.
- **drizzle-kit cannot apply these migrations.** `drizzle-kit migrate` only
  drives pg/postgres/neon/vercel and rejects the bun-sql driver, so `migrate.ts`
  runs `drizzle-orm/bun-sql/migrator` instead and drizzle-kit is used for
  `generate` alone.
- **React Compiler is a Babel preset now.** `@vitejs/plugin-react` 6 dropped its
  `babel` option; the path is `reactCompilerPreset` from the plugin, fed to
  `@rolldown/plugin-babel`. See `vite.config.ts`.
- **`client.tsx` overrides the client entry** simply by existing — the Start
  plugin resolves `src/{client,server,start,router}` and falls back to its own.
- **`validateSearch` is not the constraint people remember.** A Standard Schema
  validator (zod) typechecks under `exactOptionalPropertyTypes` with no
  ceremony. Writing the validator by hand does fail — but as plain TS2375 on the
  object you built, fixed by declaring `q?: string | undefined`, not by anything
  router-specific.
- **An open PGlite keeps `bun test` from exiting.** Every test passes and the
  process still exits non-zero; close the instance in `afterAll`.
- **`Logger.json` does not silence `BunRuntime.runMain`'s logger.** A daemon
  entrypoint prints every record twice — once as JSON, once as prose — unless the
  layer also does `Logger.remove(Logger.prettyLoggerDefault)`.
